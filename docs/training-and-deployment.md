# 训练与部署接口

复现时需要绑定同一阶段的训练配置、checkpoint、导出脚本、ONNX文件、激光预处理和动作处理。仓库保存194维Stage1与556维Stage3两类模型，不能互换。这里只说明归档中可核实的接口与准备步骤，不承诺所有历史快照开箱运行。

## 模型阶段

| 阶段 | 输入维度 | Actor隐藏层 | 输出 | 已保存依据 |
|---|---:|---|---|---|
| Stage1 | 194 | 256、256、128，ELU | 2维 | 训练快照、`export_stage1_to_onnx.py`、Stage1 ONNX元数据 |
| Stage3 | 556 | 512、256、128，ELU | 2维 | `obs_stage3.py`、导出脚本、3月25日终端输出和ONNX元数据 |

Stage1训练快照记录PPO、128并行环境、seed42、每环境16步、最大2000次迭代、学习率0.001/adaptive、gamma0.99、lambda0.95、entropy0.008、clip0.2。Actor和Critic的观测归一化均开启。Stage3终端输出记录学习率2e-4、entropy0.01及独立的512/256/128网络；完整Stage3训练工程并未完整保存在该接口目录。

Stage1仿真 `dt=0.005s`、`decimation=20`，据配置计算策略10Hz；LiDAR更新周期0.078s。真实运行测得策略话题约13—14Hz，不能把训练配置频率代替实测频率。

## 556维观测契约

以下索引为Python半开区间，使用float32。

| 索引 | 内容 | 单位及约定 |
|---|---|---|
| `[0:3]` | vx、vy、vz | m/s |
| `[3:6]` | wx、wy、wz | rad/s |
| `[6:9]` | projected_gravity | 保存的部署版本固定[0,0,-1] |
| `[9:13]` | dx_b、dy_b、dz_b、dyaw_b | 车体系米和弧度，平地保留dz=0 |
| `[13:194]` | 当前激光t0 | 181维 |
| `[194:375]` | 上一帧t1 | 181维 |
| `[375:556]` | 上上帧t2 | 181维 |

训练接口描述的目标是episode开始采样后固定不变的终点。部署版本可能输入最终目标，也可能输入全局路径的移动前瞻点；这些输入语义不完全相同。通常 `dyaw=atan2(dy,dx)` 是机器人指向目标的方位角，不是最终目标自身的姿态误差。

LiDAR主线参数是-135°至135°、1.5°间隔、181束；从-135°到135°排列。距离除以12m归一化，无命中按该阶段约定填最大值。三帧顺序为[t0,t1,t2]，t0最新。早期接口回答曾写16m，后续观测函数、终端配置和部署说明使用12m；8×8m训练房间尺寸也不能推导出8m归一化量程。

实车雷达与车体前向相反约180°的问题已通过扫描半周重排和配套aligned TF处理，位于上述裁剪与归一化之前，见[方向修正证据](deployment-problem-cases.md#lidar-frame-alignment)。另有8×8米训练场景与较大实验环境不一致的问题，后续为此实现全局路径前瞻目标与插件源码；输入接口对齐不能代替场景泛化验证，见[场景差异处理](deployment-problem-cases.md#scene-gap)。

Stage3观测函数先滚动历史，再对发生episode reset的环境用当前扫描覆盖三槽，避免旧episode的激光历史残留。

## 观测归一化与ONNX

需要区分两种归一化：激光距离除以12m属于观测构造；checkpoint中学习得到的 `actor_obs_normalizer` 均值和标准差属于进入网络前的统计归一化。保留前者不能替代后者，也不要对已带normalizer的ONNX重复处理同一份统计归一化。

Stage3导出脚本封装 `(obs-mean)/std` 与actor，丢弃critic和优化器。Stage1导出脚本使用 `(obs-mean)/(std+1e-8)`。这都是对应脚本的实现，不能按文件名假定任意导出版本数值等价。

归档中实际解析到7份ONNX：6份输入556维、1份输入194维，均输出2维。556维同名文件有两类：

- opset13、约1.80MB、内嵌权重的导出。
- opset18、主图13,750字节、配套 `.onnx.data` 的外置权重导出。部署时主图和外部权重需要一起保留。

Stage1 ONNX为opset17、输入194维。ONNX图结构读取已核实维度与算子，但仓库整理期间没有进行策略数值等价或机器人行为测试。

## 动作契约与分支参数

Stage1保存的 `diff_drive_action.py` 把raw[0]/raw[1]直接视为v/w，先按物理范围裁剪，再转左右轮速。配置记录轮半径0.1525m、轮距0.482m、线速[-0.2,1.5]m/s、角速±3rad/s。Stage3接口截图要求继续核查scale/clip内部实现，不能据截图统一解释所有阶段。

多节点部署分支则执行：角速度bias补偿 → clip[-1,1] → 线性映射到配置速度范围 → 再限幅。它与上述Stage1代码存在差异，但尚未可靠建立训练快照和部署ONNX的一一对应关系。

| 参数 | Python源码默认 | Python launch覆盖 | C++插件YAML |
|---|---|---|---|
| linear_min/max | -0.2 / 0.5 | -0.2 / 0.5 | -0.2 / 0.3 |
| angular_min/max | -0.5 / 0.5 | -0.5 / 0.8 | -0.5 / 0.8 |
| action_bias_w | 0 | -0.13 | -0.13 |
| 位置到达阈值 | 0.5m | 0.5m | 0.1m |
| yaw到达阈值 | 按该分支目标门控 | 同左 | 0.1rad |

历史4月28日运行记录的速度范围又与当前launch不完全相同，应以当次运行参数快照解释当次数据。

## 部署准备顺序

1. 从[版本说明](version-history.md)选择一个模型与代码快照，核对ONNX的输入维度、opset、外部data和normalizer。
2. 核对180°扫描重排与aligned TF是否配套，按当次TF树选择一个发布入口，避免重复旋转；再检查181束排列、12米尺度、三帧时序和goal4的四个分量。
3. 按目标分支核对真实速度来源、动作含义、映射范围和控制源切换关系。
4. 在ROS1 Noetic/catkin及对应ONNX Runtime环境中编译或加载；保存的Python包曾存在launch引用缺失同名yaml/脚本问题，应先检查文件对应。
5. 用观测真值验证与日志逐字段比对Python/C++输出，再建立受控实车验收；本次归档未代替这些验证步骤。

原节点包与插件包中均保留各自的构建说明和配置。不要同时把多个同名 `rl_planner` 包加入同一个catkin工作空间；应一次选择需要的实现。
